# HMS Entity-Relationship Overview

## Entities

| Entity | Purpose | Key |
|--------|---------|-----|
| **USERS** | Staff login / roles | `USER_ID` |
| **DEPARTMENTS** | Clinical departments | `DEPARTMENT_ID` |
| **DOCTORS** | Clinicians belonging to a department | `DOCTOR_ID` |
| **PATIENTS** | Registered patients (MRN unique) | `PATIENT_ID` |
| **APPOINTMENTS** | Scheduled visits linking patient + doctor | `APPOINTMENT_ID` |
| **AUDIT_LOG** | Lightweight action trail | `AUDIT_ID` |

## Relationships

```
DEPARTMENTS 1 ──< DOCTORS
USERS       1 ──< PATIENTS.created_by
USERS       1 ──< APPOINTMENTS.created_by
PATIENTS    1 ──< APPOINTMENTS
DOCTORS     1 ──< APPOINTMENTS
USERS       1 ──< AUDIT_LOG.actor_id
```

## Cardinality notes

- One department has many doctors; a doctor belongs to exactly one department.
- One patient has many appointments; each appointment has one patient and one doctor.
- Unique index on `(doctor_id, scheduled_at)` prevents exact double-booking of a doctor slot.
- Soft flags: `is_active` on users, departments, and doctors (CHAR Y/N) — prefer deactivate over hard delete in assessment solutions.

## Indexes (summary)

- Name lookups: `ix_patients_name`, `ix_doctors_name`
- FK helpers: `ix_doctors_department`, `ix_appt_patient`, `ix_appt_doctor`
- Schedule queries: `ix_appt_scheduled`, `ix_appt_status`
- Audit: `ix_audit_entity`, `ix_audit_created`

## Sequences

All primary keys use dedicated sequences (`SEQ_*`) with `NEXTVAL` in seed/API inserts. Assessment candidates may also propose `GENERATED BY DEFAULT AS IDENTITY` as an alternative when targeting 12c+.
